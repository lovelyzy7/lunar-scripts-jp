# 「データ引き継ぎ / Transfer Data」完成契约（EN 实测，供 JP 复刻）

> 来源：EN 客户端（user 11）+ 私服 auth-server 实测抓包（2026-10-06）。
> 目的：JP 版引继窗口「登录后不自动关闭 / 显示処理に失敗しました」的修复依据。

## 一、EN 两条流程对照

| 入口 | 语义 | 客户端 RPC | 说明 |
|---|---|---|---|
| 标题画面 Transfer Data | 旧机→新机 转移 | `UserService/TransferUserByFacebook` | 第一轮监测（仅捕获请求，服务器当时返回 NotFound） |
| 游戏内菜单 Transfer Data | 把当前数据绑定/注册到账号 | **`UserService/SetFacebookAccount`** | 第二轮监测：完整成功路径 |

## 二、游戏内流程 · 成功路径（逐步实录）

1. Menu → Transfer Data
   - 若当前数据已绑定其他账号 → Caution 弹窗：
     `Deactivate the account that is currently linked to your data and use a different account? [Yes]`
2. 点 Yes → 打开登录 WebView（私服 auth 页：`LUNAR TEAR / WELCOME BACK`，用户名+密码可预填）
3. 点 Login → auth 服：
   `authenticated user "<name>" (id=<N>)` → 302：
   ```
   fbconnect://success?access_token=<JWT>&signed_request=0.<base64({"user_id":"<N>"})>
     &expires_in=86400&granted_scopes=openid,public_profile,email&token_type=bearer
   ```
4. **客户端 WebView 处理器拦截该 scheme** → FB SDK `OnLoginComplete({"access_token":"<JWT>","user_id":"<N>",...})`
   → **弹窗自动关闭**（无需任何手动操作、无提示框）
5. 客户端调 RPC：`/apb.api.user.UserService/SetFacebookAccount`（body 携带 JWT）
6. 服务端：`linked facebook_id=<N> to user_id=<当前用户>` → 返回 OK（DB `users.facebook_id` 更新）
7. UI：**静默回到 Menu**（无成功/失败弹窗）

## 三、失败路径（重要陷阱）

FB SDK 已缓存**不同账号**的登录时：
```
OnLoginComplete({"error":"User logged in as different Facebook user."})
```
→ 流程静默终止，弹窗关闭，游戏服 **0** 条 RPC。
清除以下文件即可恢复（无需重装）：
```
/data/data/<pkg>/shared_prefs/com.facebook.AccessTokenManager.SharedPreferences.xml
/data/data/<pkg>/shared_prefs/com.facebook.login.AuthorizationClient.WebViewAuthHandler.TOKEN_STORE_KEY.xml
```

## 四、对 JP 的映射与结论

| EN | JP 对应 |
|---|---|
| FB SDK 拦截 `fbconnect://success` 并自动关闭 WebView | SE Bridge 页 + UniWebView：**没有** FB SDK，必须走 UniWebView 消息通道 |
| 游戏内（本轮）= `SetFacebookAccount` 绑定当前数据 | `/ntv/{gameId}/reg/top`（link 当前 uuid，已验证可建 link） |
| 标题画面 = `TransferUserByFacebook` 旧机→新机 | `/ntv/{gameId}/update/top`（rebind uuid → 目标账号） |

**JP 窗口不关闭的根因假设**（待验证）：
- 客户端 `WebViewDialogPresenter` 只处理两类完成信号：
  1) 游戏在创建对话框时通过 `AddUrlScheme(...)` 注册的 scheme（UniWebView 会把它转成 message 交给 C#）
  2) UniWebView JS 消息 → `webViewOnMessageReceived`
- 现有 v8 补丁让 `shouldOverride` 拦截 `nierspjp://bridge-done` 后**直接调用** `onSendMessageReceived(dialog, url)`，
  但传入的是**非 UniWebView 格式**的原始 URL → C# 解析失败 → 「処理に失敗しました」

**修复方向**（待授权后实施，二选一）：
- A. 用 frida hook `WebViewDialogPresenter.Setup`/`AddUrlScheme`，读出运行时注册的 scheme 与消息格式（kKey*/kValue* 常量值），
     让私服桥页面导航到**该 scheme**（或用 UniWebView 期望的 `uniwebview://message?...` 格式发消息）。
- B. 直接 hook `WebViewOnMessageReceived`(RVA 0x2d66fd0) 打印传入 raw 字符串，再伪造符合格式的消息。
